---
title: Approvals and events
description: How orders wait for people and outside systems, how decisions and events reach them, and how cancelling undoes their work.
---

Two node types pause an order until something outside it happens:
[Approval](/reference/nodes/#control.approval) waits for a person, and
[Wait for event](/reference/nodes/#control.wait_event) waits for a business event such as
`payment.received`. Both have a timeout. A waiting order is durable: it costs nothing while it
waits and survives restarts, and the order page lists every open wait.

## Approvals

An Approval node has a `title` (a template, default `Approve order {{order.id}}`), an `assignee`
(free text, default `manager`) and a `timeout` (default `2 days`). When it starts, the order page
shows the wait, and the approvals inbox lists a `pending` approval with the title, assignee and
order total.

The node takes one of three branches:

| Branch | When |
|---|---|
| `approved` | The decision is `approved` |
| `rejected` | The decision is `rejected` |
| `escalated` | Nobody decided before the timeout. The app shows this as **Timed out** |

The node's output (`nodes.<id>`) is the decision payload: `decision`, `by`, `note` and
`outcome`. The inbox records the outcome, who decided (`timeout` for an escalation) and the
note. Escalation only picks the branch; what happens next is up to the flow,
for example a second approval for a more senior assignee.

### Deciding

From the **order page** or the **approvals inbox** (`/approvals`), each decision has a note field
and a 5-second undo window. Nothing is sent until the window closes, so **Undo** is real: the
order never hears about a decision that was taken back. If you leave the page during the
window, the pending decision is sent then.

Decisions close two seconds before the approval times out, so the last one still arrives in time,
and the countdown counts to that moment. Ten seconds before, it reads "Decisions close in …" (and
screen readers hear it once); within five seconds the undo window shortens to fit. When decisions
close, the buttons stay in place but disabled, any note is kept, and the card says where the order
is going: "Decisions are closed; the order is going to Decline order".

The inbox filters by `pending`, `approved`, `rejected`, `escalated` (shown as **Timed out**) or `all`. Each row
says why a person is being asked, from the step that sent the order there:

- a credit check: how far over the limit, the limit and the balance, all in USD, with a
  foreign-currency order shown in its own currency and in USD;
- a budget check: how far over the budget, and the budget;
- a condition that compares the order total with a number: the threshold in words, e.g. "Over the
  $5,000.00 threshold";
- any other condition or step: the step's name and its answer.

It also shows what the order is for (its first lines), any approval steps before this one and how
they ended ("Before this: Manager approval timed out"), and when the approval times out and to which
step. When an approval times out and the next one on the same order arrives, the new one takes the
old row's place. Keyboard: `j`/`k` (or the arrow keys) move between rows, `a` approves, `r` rejects
and `z` undoes.

Deciding needs the `approver` role or higher. `by` is the signed-in person's email; see [Team and roles](/guides/team-and-roles/#who-decided).

If an admin has set **Who started an order** to **Can't approve it**, the person or token that started the order can't decide its approvals: the order page and the inbox show "You started this order, so someone else must decide its approvals." The inbox says so on the row before anyone tries, in place of the buttons. See [Approvals](/guides/team-and-roles/#approvals).

From the **API**:

```bash
curl -X POST https://orderloop.app/api/v1/orders/ord_…/approvals/approval \
  -H "Authorization: Bearer $ORDERLOOP_TOKEN" -H 'content-type: application/json' \
  -d '{ "decision": "approved", "note": "Paid last invoice" }'
```

`$ORDERLOOP_TOKEN` is an API token with the `approver` role or higher. The decision is recorded
`by` the token (`token:<name>`) or the signed-in person; the body has no `by`. A decision for a node that isn't waiting for an approval fails with
`That node is not waiting for an approval`, and one on an order the caller started, with separation on, fails with `403`. See the [REST API](/reference/rest-api/).

The [assistant](/guides/assistant/) can decide an approval for an `approver`, but only after the
person confirms a card showing the order and where each decision leads (the card is blocked, with the reason, when the person started the order and approvals are separated). There is no undo window
for a decision made there, and the decision is recorded `by` `<email> via assistant`.

## Waiting for events

A Wait for event node names an `event` (default `payment.received`) and a `timeout` (default
`30 days`). It takes `received` when the event arrives and `timeout` otherwise.

The event's payload is stored in the run variables under the event name with every run of
non-alphanumerics replaced by `_`: `payment.received` → `vars.payment_received`,
`return.requested` → `vars.return_requested`. Later nodes read it from there; the storefront
flow's Refund node, for example, takes `vars.return_requested.amount`. OrderLoop adds `event` and
`at` (epoch ms) to every delivered payload.

### Delivering an event

An event is delivered to whichever node is waiting for that event name. If none is, nothing
happens and the caller is told `delivered: false`; delivering again later works once a node is
waiting.

- **Order page**: the open wait says what it waits for in plain words and has a button that
  records it by hand, such as **Mark as collected** for `pickup.collected` or **Record payment** for
  `payment.received` (payload `{ "source": "dashboard", "amount": <order total> }`). The event name
  and the API endpoint are under **For developers**.
- **Commerce page**: lists the events the 20 most recently updated waiting orders wait for, with each
  order's customer and total, and the same button as the order page. Nothing is sent for five
  seconds, so **Undo** takes it back; leaving the page sends it at once. The payload is
  `{ "source": "commerce" }`. Seller responses on a marketplace order are recorded per seller on
  the order page.

The Commerce page's **Records** section shows what orders have done outside the flow, newest first:
money (payments, invoices and seller payouts), shipments, stock holds, seller orders, messages sent
and documents. Each row names its order and, for connector writes, the step that wrote it
(`capture#1`): a retried step finds that same record rather than writing another. The search box at
the top of the page finds an order, customer, SKU or seller across every section. Long lists
(inventory, each store's stock, each pricing source, customers and sellers) show a page at a time,
with **Previous** and **Next** under them; each keeps its own page, so paging one leaves the others
where they are.
- **REST API**, with an API token of the `operator` role:

  ```bash
  curl -X POST https://orderloop.app/api/v1/orders/ord_…/events \
    -H "Authorization: Bearer $ORDERLOOP_TOKEN" -H 'content-type: application/json' \
    -d '{ "event": "payment.received", "payload": { "amount": 3106.78 } }'
  ```

  The response is `{ "delivered": true, "nodeId": "…" }` or `{ "delivered": false }`.

- **Signed webhook**, for external systems that shouldn't hold an API token:
  `POST /api/v1/webhooks/events` with the body signed by an [integration's](/reference/rest-api/#integrations) key.

### Signed events

Each external system gets its own integration: an admin creates it with
[`POST /api/v1/integrations`](/reference/rest-api/#integrations), which returns its `id` and a
signing secret (`whsec_…`) shown once. The integration limits what the system may do: the events it
may deliver (`events`, or `["*"]` for any), and optionally one `channel`, in which case it reaches
only orders on that channel. A payment provider's key can deliver `payment.received` and nothing
else.

```
POST /api/v1/webhooks/events
X-OrderLoop-Signature: t=<unix seconds>,k=<integration id>,v1=<hex HMAC-SHA256(secret, "<t>.<raw body>")>

{ "orderId": "ord_…", "event": "payment.received", "payload": { "amount": 3106.78 } }
```

The timestamp is part of the signed message and must be within 5 minutes of the server's clock,
so a captured request can't be replayed later. `k` is the integration's `id`; it tells OrderLoop which secret to check. The signature of a delivered event is also recorded, so replaying it within the window returns `200 { "delivered": true, "duplicate": true }` and delivers nothing; a `409` is not recorded and may be retried.

| Status | Meaning |
|---|---|
| `200` | `{ "delivered": true, "nodeId": "…" }` |
| `409` | `{ "delivered": false }`: no node is waiting for that event yet, so retry later |
| `400` | The body isn't `{ orderId, event, payload? }`, or `payload` is over 32 KiB of JSON |
| `413` | The body is over 1 MiB |
| `401` | Missing or malformed header, no `k=`, an unknown or revoked integration, stale timestamp, or wrong signature |
| `403` | The integration may not deliver that event, or is bound to a channel other than the order's |
| `404` | No such order, or (for a channel-bound integration) not one it can see |
| `429` | The integration sent more than 1,200 requests in a minute (inbound orders included); retry after `Retry-After` seconds |

Answering `409` lets the sender's own retry policy deliver an event that arrives before the order
reaches its wait.

### Stripe events

Stripe doesn't sign with an integration key, so it has its own endpoint,
`POST /api/v1/webhooks/stripe`, verified with the `Stripe-Signature` header and the endpoint's
signing secret. During a secret roll Stripe sends a signature for each secret; any one that matches
passes. The deployment's operator registers the endpoint in Stripe and enables three events:

| Event | What OrderLoop does |
|---|---|
| `invoice.paid` | For an invoice an order issued through Stripe (see [Payments](/guides/payments/#invoices-paid-through-stripe)): marks it paid, records the payment, settles the account charge, and delivers `payment.received` to the order (payload `provider`, `invoiceId`, `invoiceNumber`, `amount`, `currency`) |
| `payment_intent.canceled` | Marks the order's payment authorization `voided` |
| `charge.dispute.created` | Delivers `payment.disputed` (payload `disputeId`, `amount`, `currency`, `reason`) when a node is waiting for it; otherwise it is noted and nothing else happens |

Each Stripe event id is acted on once; a redelivery answers `200` with `{ "outcome": "duplicate" }`.
Events about invoices or payments OrderLoop didn't create, and other event types, answer `200`
with `{ "outcome": "ignored" }`. When `invoice.paid` arrives before the order reaches its
`payment.received` wait (the customer paid while it waited for an approval, say), the invoice is
settled and the answer is `409`: Stripe delivers the event again later (it keeps trying for three
days) and it resumes the order then. Once the order has ended, the event is settled and not
retried. A bad signature answers `400`, and `503` means Stripe webhooks aren't configured on the
deployment.

Decisions, delivered events and cancellations are recorded in the
[audit log](/guides/team-and-roles/#audit-log) with how they came in (the app, the REST API, a
signed webhook, the assistant, MCP or A2A). An event nothing was waiting for is not.

## Cancelling

Cancel from the order page, the API (`POST /api/v1/orders/:id/cancel` with an optional `reason`),
or the [assistant](/guides/assistant/) (after the person confirms). Cancelling an order that has already
ended, or one that is already being cancelled, does nothing. Otherwise OrderLoop:

1. stops the run;
2. undoes the order's work: releases its inventory reservations, voids its payment
   authorizations, cancels its open shipments and staged store pickups, restocks stock those
   shipments consumed once none is live, voids its unpaid Stripe invoices (a paid one is left
   alone and named in the timeline), reverses its on-account invoice charges, revokes its
   issued digital codes, cancels its seller orders and reverses its scheduled payouts;
   If a shipping provider cannot void a label, the shipment is not marked cancelled, the
   timeline says how many labels could not be voided with their provider, and OrderLoop tries
   again daily;
3. marks pending approvals `cancelled` and clears the order's waits;
4. sets the status to `cancelled`, with the reason and the counts in the timeline;
5. sends the `order.cancelled` [outbound webhook](/guides/outbound-webhooks/).

Captured or charged money isn't refunded by a cancel; refunds are a node in the flow.

Cancelling is different from an order that fails: a failure runs each completed step's rollback in
reverse order (see [Ending a run](/guides/building-flows/#ending-a-run)) and ends `rolled_back`.
