A flow is a JSON graph of [catalog nodes](/reference/nodes/) and the edges between them. The
editor at `/flows/:flowId` saves it as a draft. Publishing snapshots the draft as an
immutable, numbered version, and every order pins the version it started on.

## Creating a flow

**New flow** on `/flows` takes a name, a [commerce model](/guides/commerce-models/) (<Values of="order-models" />) and a
starting point:

| Start | What you get |
|---|---|
| Template | The [built-in flow](/guides/templates/) for that model |
| Blank | One `trigger.manual` node named `start` |
| Describe it | A graph drafted by the [copilot](/guides/ai/#the-flow-copilot) from your description, laid out automatically |

The flow id is a slug of the name plus a short suffix. A new flow is a draft until you publish it.

## The editor

- **Palette.** Every node type in the catalog, grouped as Triggers, Commerce, Control and AI.
  Drag one onto the canvas.
- **Canvas.** Each output branch of a node is its own handle; an edge leaves from
  the branch it belongs to. A `control.loop` node has a second input, `next`, for its back-edge.
- **Inspector.** The selected node's label and config fields, generated from the node's catalog
  entry, plus its per-node `retries` and `timeout`. Validation messages appear beside the field.
  While the assistant panel is open, the inspector folds away to give the canvas room, and comes
  back when you select a node.
- **Ask.** Opens the [assistant](/guides/assistant/) about this flow, with the graph on screen
  (unsaved changes included) as context. A change it proposes ("add a fraud check after credit")
  comes back to the editor as a proposal that shows what it adds, removes, edits and rewires;
  nothing changes until you accept it, and accepting is one undoable edit.

**Save** stores the draft and returns the current validation errors and warnings. **Publish**
asks for confirmation, then publishes the next version. **Test run** publishes too when the graph
differs from the published version, then starts a sample order on it: the input of the first
[dashboard scenario](/guides/templates/#scenarios) that uses this flow, else the first one for its
model, else an empty `manual` order. A workspace without the demo data has no scenarios, so the
test run starts an empty order.

The built-in templates publish themselves again when they change, replacing edits made to them
here (see [Seeding](/guides/templates/#seeding)). To customise one, make your own flow from it.

## Validation

Validation runs in the editor as you edit, on save, and before publishing. Publishing is refused while there are errors.

Errors:

- A node id appears twice, or a node's type isn't in the catalog.
- A config field is missing when required, or fails its kind's check (see the
  [node catalog](/reference/nodes/) for each field's kind).
- The flow doesn't have exactly one trigger, or an edge points into a trigger.
- An edge points at a missing node, or leaves from an output the source node doesn't have.
- Forward edges form a cycle. Repeating steps needs a Loop node with a `next` back-edge.
- A `next` edge targets anything but a Loop node, or comes from outside that loop's body.
- A non-trigger node has no incoming forward edge.

Warnings, which don't block publishing: a duplicate edge, and a node with outputs but no
outgoing edge ("the run ends there").

## How a run moves through the graph

- **Branches.** A node finishes by choosing its output branches: `true`/`false` for a
  Condition, `approved`/`rejected`/`escalated` for an Approval, one route for the Agent router,
  `out` for single-output nodes. Edges on the chosen branches become active; the rest become
  inactive.
- **Joins.** A node with several inputs runs once every input is resolved and at least one is
  active. So a node after an `if/else` runs once, whichever side was taken.
- **Skips.** A node whose inputs are all inactive is skipped (status `skipped`), and so is
  everything downstream that depends only on it.
- **Parallel work.** Every node that is ready at the same time starts in the same batch.
- **Loops.** A Loop node evaluates `while` each time it is entered, up to `maxIterations`. On
  `body` it runs the nodes reachable from its `body` output; the last of them connects back to the
  loop's `next` input. When the condition is false (or the limit is reached) it takes `done`. Each
  iteration runs afresh; an iteration never reuses an earlier one's results.
- **Continue as new.** `control.continue_as_new` ends the current run and starts a new one on the
  same flow version, with the order and variables carried over. The order keeps its id; its
  `generation` goes up by one. Use it for long-lived loops such as subscriptions, so the run's
  history stays bounded.

## Ending a run

A `control.end` node finishes the order with an outcome:

| Outcome | Order status | Notes |
|---|---|---|
| `completed` | `completed` | The normal ending |
| `declined` | `declined` | A policy or approval "no": not a person cancelling |
| `cancelled` | `cancelled` | Ends the run as cancelled |
| `failed` | `failed`, then `rolled_back` | Runs every completed step's rollback, in reverse order |

`reason` is a template and becomes the order's reason. Every End node also sends the matching
`order.<outcome>` [outbound webhook](/guides/outbound-webhooks/). A run whose remaining nodes
are all skipped, with no End node reached, finishes as `completed`.

A commerce node that still fails after its retries fails the order the same way, without reaching an
End node. Only nodes tagged **undo** in the [node catalog](/reference/nodes/) have rollbacks: reserve inventory
(releases the reservation), authorize payment (voids the hold), create shipment and ready for
pickup (cancel the shipment or staged pickup, and restock what it consumed), generate invoice (voids an unpaid Stripe invoice and takes an on-account charge back off the balance), deliver digital goods (revokes the codes), split by
seller (cancels the seller orders) and seller payouts (reverses scheduled payouts).

## Expressions and templates

Condition, Wait (`until`), Set variables, Loop (`while`) and Refund (`amount`) take
[JSON Logic](/reference/expressions/) expressions. Text fields interpolate `{{path}}` templates,
for example `Approve order {{order.id}}`. Both read the run context:

| Path | Holds |
|---|---|
| `order` | The order: lines, totals, `customerId`, `currency`, `meta`, … as nodes update it |
| `nodes.<id>` | The output of each node that has run (latest iteration) |
| `vars` | Run variables: set by Set variables, AI nodes (`into`), event payloads, and the `vars` passed when the order starts |
| `input` | The order's `meta` |
| `now` | When the current run started, epoch ms |
| `ref` | How the customer knows the order: its outside number (`externalId`), else its title, else its id. The built-in flows use it in customer emails |

The [expressions reference](/reference/expressions/) has the operators and the policy rules.

## Retries and timeouts

Each commerce, AI, Condition and Set node runs as one durable step. Its retry limit is the node's
`retries`, else the node type's default (`commerce.charge` has `0`), else `3`, with a 5-second
exponential backoff. Its timeout is the node's `timeout`, else `"5 minutes"`. Approval,
Wait-for-event and Wait nodes don't use these; their waits have their own `timeout` field.

## Publishing and versions

Saving a draft on purpose (**Save** or ⌘S, not an autosave), publishing, and test runs are recorded in the [audit log](/guides/team-and-roles/#audit-log); each version keeps who published it.

Publishing saves the draft and stores it as the flow's next version. Versions are immutable. An order started through the API runs the latest published version
unless the request names one (`version`); a running order keeps its version even after you
publish again. Restarting an order from its page starts a new order on the flow's current
version, with the same customer and lines and without `meta.simulate`.
